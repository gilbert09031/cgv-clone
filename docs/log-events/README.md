# 로그 이벤트 카탈로그

이 디렉터리는 프로젝트의 로그 이벤트를 도메인별로 설계하고, 구현과 함께 지속적으로 관리하는 카탈로그다. 이 README는 새 작업에서 참고할 설계 기준과 문서 탐색의 시작점이다.

이벤트가 어떤 사건을 의미하는지, 언제 기록되는지, 어떤 필드로 연결하고 검색하는지를 명시한다. 설계한 계약과 현재 구현·검증 상태를 구분하여, 이후 작업자가 코드와 관측 도구의 동작을 같은 기준으로 이해할 수 있게 한다.

## 사용 방법

로그를 추가하거나 수정할 때 다음 순서로 확인한다.

1. [공통 계약](common.md)에서 공통 필드, 요청·오류 이벤트, 민감정보 규칙을 확인한다.
2. 대상 도메인 문서에서 같은 사건을 표현하는 기존 이벤트를 찾는다.
3. 실제 호출 흐름, 상태 변화, 트랜잭션·외부 호출 경계를 확인하고 관측할 사건을 정한다.
4. 이벤트의 의미·레벨·필드·기록 책임·시점을 도메인 문서에 작성하거나 갱신한다.
5. 구현 후 로그 출력과 검색 결과를 검증하고, 구현 상태와 검증 근거를 함께 갱신한다.

문서에 정의된 이벤트가 모두 구현되어 있다는 뜻은 아니다. 작업 시작 시 문서의 상태와 현재 소스를 함께 확인한다.

현재 카탈로그는 좌석 예매 흐름부터 문서화되어 있다. 이는 초기 작성 범위이며, 프로젝트 전체의 로그 이벤트를 관리하는 목적을 제한하지 않는다. 로그인·인증, 관리자 작업, 매점 주문, 결제 취소 등은 관련 작업을 진행할 때 기존 도메인 문서를 확장하거나 새 문서를 추가한다.

상영 일정과 상영 좌석은 현재 코드의 `domain/reservation`에 속하므로 예약 문서에서 관리한다. 하나의 요청에서 여러 도메인의 이벤트가 발생해도 각 이벤트는 사건을 소유한 도메인 문서에 정의하고, 관련 흐름은 문서 링크와 식별자로 연결한다.

## 관측 목표

- 요청 단위로 응답 상태, 실패 원인, 지연 구간을 확인한다.
- 요청 상태·지연 집계는 메트릭, 개별 요청의 구간별 진단은 Tracing을 사용한다. 정상 요청 종료 로그는 기록하지 않고, 예상 가능한 요청 거절은 최종 경계의 DEBUG 진단 이벤트로만 남긴다. 오류 로그는 RequestID로 연결한다.
- 도메인 식별자로 여러 요청·작업에 걸친 상태 변화를 연결한다.
- 하나의 작업과 개별 시도·재시도를 구분한다.
- 외부 시스템 실패, 결과 불명, 내부 기록 실패를 구분한다. 예상 가능한 요청 거절은 응답으로 전달한다.
- 상태 변화와 자원 확보·반환을 실제 처리 결과로 확인한다.

각 도메인 문서에는 해당 이벤트로 답하려는 질문을 구체적으로 적는다. 로그가 없다는 사실만으로 실패나 사용자 이탈을 확정하지 않으며, 서버에서 관측할 수 없는 사용자 행동이나 외부 시스템 상태는 관측 한계를 명시한다.

## 이벤트 정의 항목

새 이벤트를 정의할 때 아래 항목을 작성한다. 도메인 문서의 표 형식은 사건의 특성에 맞게 구성하되 이 정보는 유지한다.

| 항목 | 작성 기준 |
|---|---|
| 이벤트명 | `resource.action` 형식의 고정된 이름. 같은 사건에 기존 이름이 있으면 재사용 |
| 의미·발생 상황 | 어떤 사건을 나타내며, 어떤 조건에서 발생하는지 명시 |
| 로그 레벨 | 정상 상태 변화·예상 가능한 거절·시스템 오류를 구분하고 선택 근거 설명 |
| 기록 책임·시점 | 기록을 소유한 경계와 호출 전·후, 커밋 후 등의 시점 명시 |
| 필드 | 필수·선택 여부, 타입, 의미, 단위, 허용 값과 알 수 없을 때의 처리 명시 |
| 연결 식별자 | 요청·도메인 객체·작업 시도 사이를 연결할 식별자 정의 |
| 중복·집계 기준 | 발생 횟수, 재시도·중복 요청 처리, 집계할 대표 이벤트 명시 |
| 구현 상태·근거 | 설계와 현재 동작의 차이, 소스 위치, 검증 날짜·결과 기록 |

공통 규칙은 공통 문서를 참조하고, 도메인 문서에는 추가 필드와 예외 사항을 적는다. 이벤트 이름만 나열하거나 모든 메서드의 진입·종료를 이벤트로 만들지 않는다.

## 구현 상태 표기

| 상태 | 의미 |
|---|---|
| `기존·보완` | 같은 이름의 로그가 있지만 필드, 레벨 또는 기록 시점을 이 문서에 맞춰야 함 |
| `추가 예정` | 현재 코드에 해당 이름의 이벤트가 없음 |
| `공통 적용` | 도메인별 이벤트를 새로 만들지 않고 공통 이벤트로 관측 |
| `구현 완료` | 문서 계약에 맞는 출력·발생 조건·기록 시점을 검증하고 근거를 기록함 |

`기존·보완`은 목표 계약을 충족했다는 의미가 아니다. `공통 적용`도 해당 공통 이벤트의 구현 완료를 보장하지 않는다. 설계 중인 문서는 초안임을 표시하고, 구현 완료와 로그 수집·검색 검증 여부를 구분한다. 검증 근거에는 적용 환경과 날짜를 남겨 과거 결과를 현재 환경의 증거로 오해하지 않도록 한다.

## 설계 원칙

1. **요청 관측과 도메인 사건을 구분한다.** 정상 조회의 상태·지연은 메트릭·Tracing으로 관측하고, 필요한 상태 변화는 도메인 이벤트로 기록한다. 정상 종료 로그는 추가하지 않으며, 예상 가능한 요청 거절은 공통 DEBUG 진단 이벤트로만 남긴다.
2. **저장 성공을 의미하는 이벤트는 DB 커밋 후에 기록한다.** 메서드 내부의 상태 변경만으로 저장 성공을 선언하지 않는다. 외부 호출 결과는 내부 저장 결과와 별개로 기록한다.
3. **하나의 실패 원인에 대한 상세 로그·스택 트레이스는 한 곳에서 기록한다.** HTTP 실패 요약과 도메인 상세 오류를 합산해서 실패 건수를 계산하지 않는다.
4. **식별자는 의미가 드러나는 이름을 쓴다.** 도메인 객체와 외부 시스템·시도 식별자를 구분한다. 예를 들어 서버 결제 번호 `paymentNumber`와 외부 주문 식별자 `gatewayOrderId`를 같은 의미로 취급하지 않는다.
5. **실제 JSON 필드로 출력한다.** 문자열 `message` 안의 `event=...`를 독립된 JSON 필드로 간주하지 않는다.
6. **공통 필드는 최소화한다.** `event`와 HTTP 요청의 `requestId`만 기본으로 요구한다. 나머지는 이벤트별로 선언하고 실제 반복 사용을 확인한 뒤 공통 승격을 검토한다. 작업은 이벤트명·라우트로 구분하며 `operation`·`domain`·`stage` 등을 일괄 추가하지 않는다.
7. **설계와 구현 사실을 구분한다.** 아직 구현되지 않은 기능의 이벤트는 제안임을 명시하고, 현재 발생하는 이벤트나 상태 전이처럼 설명하지 않는다.

일반 작성 규칙은 [로깅 컨벤션](../LOGGING_CONVENTION.md), 공통 출력·필드·민감정보 계약은 [공통 문서](common.md), 개별 사건의 의미와 시점은 도메인 문서를 참고한다. 규칙 간 차이를 발견하면 변경 대상과 현재 차이를 명시하고 관련 문서를 함께 갱신한다. 문서 수정만으로 실제 출력이나 수집 설정이 바뀌었다고 간주하지 않는다.

## 유지·업데이트 규칙

- 이벤트를 추가하거나 변경하는 PR에서 해당 도메인 문서도 함께 수정한다.
- 새 도메인 문서를 추가하면 이 README의 문서 목록과 문서화된 범위도 갱신한다. 구체적인 API 목록·호출 흐름은 해당 도메인 문서에서 관리한다.
- 각 이벤트의 이름, 레벨, 발생 상황, 기록 책임, 시점, 필수 필드, 현재 상태를 유지한다.
- 이벤트명·필드명·타입·발생 의미를 바꾸면 기존 검색·대시보드·알림 영향과 전환 방법을 기록한다.
- 로그 이름이 코드에 있다는 이유만으로 구현 완료로 바꾸지 않는다. JSON 출력, 커밋 경계, 중복 기록 여부를 검증한다.
- 런타임 검증에는 날짜, 환경, 재현 시나리오, 파일 출력·수집·조회 결과를 기록한다. 소스 확인과 런타임 검증을 구분한다.
- 소스 링크는 심볼을 함께 적는다. 코드가 이동하면 링크와 책임 위치를 같이 갱신한다.

## 검증 기준

이벤트의 의미에 맞는 시나리오를 선택하여 검증한다. 검증하지 못한 항목은 완료로 표시하지 않고 남은 범위를 기록한다.

| 시나리오 | 확인할 계약 |
|---|---|
| 정상 처리 | 식별자로 요청·상태 변화·후속 작업을 연결할 수 있음 |
| 입력·권한·도메인 검증 거절 | 기존 오류 응답·RequestID가 유지되고 최종 경계의 DEBUG 진단 이벤트만 남으며 종료 로그와 성공 상태 전이 이벤트가 없음 |
| 트랜잭션 롤백 | 저장에 실패한 상태 변화의 성공 이벤트가 없음 |
| 외부 시스템 거절·오류 | 외부 결과와 내부 기록 결과를 구분할 수 있음 |
| 타임아웃·결과 불명 | 결과를 모르는 경우를 확정 실패나 성공으로 기록하지 않음 |
| 외부 처리 후 내부 기록 실패 | 외부 처리 사실과 내부 기록 오류가 연결됨 |
| 재시도·중복 요청 | 개별 시도와 최종 결과를 구분하고 상태 변화·집계가 중복되지 않음 |
| 로그 전송·검색 | JSON 필드 조회, 식별자 연결, timestamp 처리, 민감값 미노출 확인 |
